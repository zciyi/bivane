### 真机探针抓到的缺陷（通过前四门 + 288 单测）

**区间模式打开时滚轮停在「今年 1 月 1 日」而不是今天。**
`resolveCursor` 无值兜底写的是 `{year: today.year, month: 1, day: 1}`。区间模式的两段式草稿恒以 `''` 开场
→ 这是**主路径**；列裁剪形态同样走它；**单值形态因为分发层预填了今天，把这条路径整个盖住了**。
实测证据：H5 区间展开 `选择月份.selected=01`、`选择日期.selected=01`；PC 区间/单值展开月历标题「2026 年 1 月」。
**更值钱的教训：`tests/date-value.test.ts` 当时把实现的行为当规格抄进了断言**
（`expect(resolveCursor(undefined, …)).toEqual(D(today.year, 1, 1))`）—— 断言来自「我看到什么」而不是
「我期望什么」，等于给缺陷上锁。修法：兜底改 `{...today}`，列裁剪补位仍由后续几行负责；测试改正向断言 +
补两例列裁剪兜底。

另修：区间高亮只接「起点 + 悬停终点」，**已提交区间反而没底色**（实现期自捕获）→ `displayRange` 覆盖两种来源。

### 17:27 复盘问答：DatePicker 日期/日历逻辑是自写还是复用的？

结论（已查实）：**100% 自写（除 PC 浮层用 Radix Popover 的 Anchor）。** 仓库无任何日期库（dayjs/date-fns/moment/luxon/react-day-picker 均不依赖；`moment` 字符串命中只是 `use-picker-column.ts` 注释里的 momentum 惯性）。
分层：① 日期运算（解析/格式化/min-max 逐字段夹紧/区间排序/6×7 网格推算）`use-date-value.ts` 536 行纯函数；② 滚轮列 `use-picker-column.ts` 156 行 + H5 端，原生动量+`scroll-snap`，无第三方等价（Vant 自己也是自研 Picker）；③ 月历网格 PC 端 401 行自绘，react-day-picker 是真实可替代项但自带 DOM/a11y 模型，覆盖 Vant 语义成本 > 自写；④ 浮层/锚定/焦点交 Radix Popover。
为什么零日期依赖：copy-paste 分发模型下每个 runtime 依赖会随 registry 进消费者项目，白名单锁 8（已弃 vaul、@use-gesture）。且 Vant 本身也不用日期库。唯一值得引入库的是 ① 的 536 行纯函数（date-fns/@internationalized/date 降边界风险），但破白名单。边界已用 37 例 date-value 测试 + 门 6/7 探针覆盖（「滚轮停 1 月」即此路径抓到）。
MEMORY 里 `packages/vant/src/...` 路径已失效 → 改记为「Vant 只是交互语义事实源，无本地源码」。

### 17:45 选型问答：MUI X Date Pickers vs react-day-picker

用户问二选一。结论：**Bivane 选 react-day-picker，否决 MUI X。**
理由（查实 @mui/x-date-pickers v9.12.0）：MUI X 强制 peer `@mui/material`+`@emotion/react`+`@emotion/styled`+某日期库(dayjs/date-fns/luxon/moment)，还需在**应用根部**包 `LocalizationProvider`（React context），且是 Material Design 视觉、装包 ~3.7MB。这与 Bivane 四件硬约束全冲突：Tailwind（非 Emotion）、Vant 视觉（非 Material）、copy-paste 分发（非「包整棵 App + 带框架」）、8 依赖白名单（MUI 直接 +4~5 个）。唯一 MUI 优势是有 DateTimePicker/TimePicker 现成——但 Bivane 的 TimePicker 本就是 P2 计划内的自研滚轮（模式 C），且 Vant 的日期选择是「日期+列」混合，MUI 的 Material 时间 UI 反而要改造去贴 Vant。rdp 是 headless/小体积/Tailwind 友好/可重主题到 Vant，且自带区间悬停预览正好覆盖现有 `inRange` 逻辑。rdp 的短板是「只做日期、不做时间」→ 时间部分交我们的滚轮（与 P2 路线图一致）。
