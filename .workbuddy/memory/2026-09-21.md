## P2 DropdownMenu 落地（模式 C 的第二种成因）

- **归属**：模式 C。判据不是「容器不同」而是**导航范式不同** —— 菜单是一棵树，H5 屏幕窄只能整层面板推入（下钻 + 返回），PC 必须留着父层（子菜单右展 + 父行保持高亮）。
- **落盘**：`hooks/use-menu-state.ts`（纯函数：路径下钻 `resolveMenuPanels` / 失效截断 / `collectMenuLeaves` / `findMenuOption`）、`components/ui/menu-parts.tsx`（共用零件）、`components/h5/menu.tsx`（Popup + 面板栈推入）、`components/pc/menu.tsx`（Radix DropdownMenu）、`components/responsive/dropdown-menu.tsx`（分发层）。
- **状态归属**：路径状态留在 H5 内部（分发层只管 open）。**别照抄 Select 的 `value` 归属** —— 状态该留在哪层取决于它是否跨模式同义。
- **槽名三分**：`menu-panel`（PC 主浮层）/ `menu-subpanel`（PC 子菜单）/ `menu-layer`（H5 面板层）。最初 H5 也写 `menu-panel`，导致「H5 不该出现 PC 浮层」断言假失败 + 动画命中错对象。

### 踩坑一：Radix Trigger 走 `onPointerDown`（且 Slot 会注入 `disabled: false`）

- Trigger 是 `onPointerDown: … context.onOpenToggle()`，**用 `fireEvent.click` 永远打不开**，现象是「面板不存在」，极易误读成组件没渲染。
- Radix 会给子元素注入 `disabled: false`（`const { disabled = false, ...triggerProps } = props`），经 Slot 合并**覆盖**我们传给 `MenuTrigger` 的 `disabled` → PC 禁用态静默失效。必须给 `DropdownMenuPrimitive.Trigger` 也传 `disabled`。
- `SubContent` 类型里**没有** `side`/`align`（恒右展），只暴露 `sideOffset` / `avoidCollisions`。

### 踩坑二（最费时、最易误诊）：jsdom 补抛的 window blur 会把刚打开的菜单关掉

- **误诊过程**：现象是「同一测试文件里，从第二个用例起菜单打不开」。先后怀疑 `asChild` 不转发 props、`modal`、userEvent 点击序列、Radix 在 unmount 后失效 —— 全错。
- **真相**：`@radix-ui/react-menu` 在打开期间订阅 window 的 blur 并 `onOpenChange(false)`（当作「用户切走了窗口」）。而 **jsdom 会在「带焦点的子树被移除」之后补抛一个 `window` 的 blur**（浏览器不会）。用例一卸载时留下带焦点的浮层 → blur 在下一个用例 open 之后才派发 → 正好被新挂载的菜单收下。
- **定位手法（值得复用）**：在 `onOpenChange` 里 push `new Error().stack` + `React.useId()` 实例号。栈里只有 jsdom 自身帧、且实例号是**新树**的 → 立刻排除「handler 失效」这类猜测。（早前用「面板是否存在」判断，5 个探针全在猜。）
- **修复**：`tests/setup.ts` 对 window 的 blur 做 `stopImmediatePropagation()` 截断（靠注册顺序抢在 Radix 前），并写下成因注释。
- **同源时序坑**：Radix roving focus 把巡航落点写在 `setTimeout(() => focusFirst(nodes))` 里，键盘断言必须 `await`，同步断言会读到旧焦点。

## DropdownMenu 触发器层级回显（用户报障「选中没有层级展示」）

## DropdownMenu 打开即定位（用户报障「打开弹窗需要定位到对应位置」）

- **判读**：紧接「触发器层级回显」的上下文，取「展开时自动定位到选中项所在位置」两层含义 —— ① 进入选中项所在**层级**（H5 面板栈直接下钻；PC 自动铺开子菜单链）；② 把选中项**滚入视野**。回显解决「看得到」，定位解决「打开就到位」；与 Select 既有行为（`initialActiveIndex` + `scrollIntoView({block:'nearest'})`）对齐。
- **归属**：`initialPath`（选中项的**祖先 value 链**）由分发层从 `selectedPath` 派生 —— 「选中值」跨模式同义，其派生量也归分发层；两端各自持有落位状态（H5 `path`、PC `openPath`）。`initialPath` 成为 `MenuPanelProps` 的**必填**字段。
- **只在 open 翻转那一刻定位**：两端都用 `wasOpen` ref 守住，避免暂存模式改草稿时把用户滚开的视野弹回；关闭即收回（PC 置 `[]`、H5 置 `[]`）。
- **PC 子菜单改为受控**：`open={openPath[depth] === item.value}`，`onOpenChange` 里按 depth 截断，保持「同层只开一条链」。

### 踩坑三：Radix `FocusScope` 延迟自动聚焦 → 刚铺开的子菜单链被立刻收回

- **症状**：`initialPath=["move"]` 一度写进 `openPath`（render 日志可见），下一帧又被置回 `[]`；`aria-expanded=false`、`subpanels=0`、滚动调用为空。
- **定位手法**：在 `onOpenChange` 里 push `new Error().stack` → 栈指向 `react-menu:751` → `react-dismissable-layer:86` → `focusoutside`；再加 `focusin` 监听打印 `event.target` → 目标是**根面板 DIV**（`data-slot="menu-panel"`）。
- **根因**：`FocusScope` 的 `container` 是 `useState`，mount 自动聚焦发生在 container 落地的**下一次提交**，**晚于**子面板挂载。于是次序是「子面板挂上 focus-outside 监听 → 根面板才聚焦」，这次 `focusin` 落在子菜单之外 → Radix 默认 `onFocusOutside` 关掉刚展开的子菜单。
- **修复**：`SubContent` 的 `onFocusOutside` 里 `if (event.target === panelRef.current) event.preventDefault();` —— 焦点落在**面板容器本身**（而非某个菜单项）说明是自动聚焦，放行这一次；落到菜单项上仍按 Radix 默认收回。

### 踩坑四：Radix `Presence` 状态机使面板 ref 晚到 → 滚动静默失效

- **症状**：依赖 `[open, openPath]` 的滚动 effect 里 `panelRef.current === null`；给 `Content` 加 ref 日志后实证 ref 在 effect **之后**才被调用。
- **根因**：`@radix-ui/react-presence` 用 `useStateMachine`，`present` 翻转靠 `useLayoutEffect` 推进 → 节点**晚一两次提交**才挂上（`MenuPortal` + `MenuContent` 各一层 `Presence`，故两次）。effect 在那一刻拿到的 ref 还是 null，等节点挂上时依赖又没变，滚动**永远不会发生**。
- **修复**：删掉滚动 effect，把「滚入视野」挪进面板的 **ref 回调**（挂载即滚）。ref 回调必须**引用稳定**（`React.useCallback` / 按 value 缓存的 `getSubPanelRef`），否则内联箭头每次渲染换身份 → React 先以 null、再以节点各调一次 → 无关渲染反复触发滚动，把用户手动滚开的视野拽回来。
- **可复用教训**：**凡在 Radix 受控浮层上做「打开即定位 / 打开即滚动」，先假设节点不会在同一个提交里出现**。jsdom 不做布局，单测只能断言「滚的是哪个元素、用什么对齐」，真机行为必须靠探针。
- **回归**：`tests/dropdown-menu.test.tsx` 新增 `describe('打开即定位到选中项')` 7 例 + `captureScrolls()` 辅助（替 `Element.prototype.scrollIntoView` 收集调用与参数）。用例数 214 → **221**。
- **验证配套**：`scripts/visual-check.mjs` 的 `probeMenu()` 补 `selectedDepth`（H5 取 `menu-layer` 的 `data-depth`，PC 取开着的 `menu-subpanel` 数）与 `selectedInView`（选中行 rect 是否落在滚动容器内，容 1px 亚像素）两项**症状级**指标 + **7g** 场景。实机：PC `selectedDepth=1` / `selectedInView=true` / `subpanel side=right` + `parentStillThere=true`；H5 `layerDepths=["0","1"]` / `trackTransform=-390px` / `headerTitle="移动到"` / `selectedInView=true`。

## DropdownMenu 头部层级面包屑（用户需求「弹窗上面加上层级，用户可点任意层级切到对应层」）

- **判读**：H5 底部抽屉的**头部**要铺出「根 → 当前层」整条层级链，点任意祖先层**直接切到该层**（不必逐层按返回）。PC 不涉及 —— 它是锚定浮层，父层本就留在原位可点，没有「弹窗上面」这一处。
- **分层（照架构 §6.5 ③）**：**渲染与样式归共享零件** `PanelHeader`（结构化 prop `breadcrumb?: { label; onSelect? }[]` + `breadcrumbLabel`，默认「层级」；给了 `breadcrumb` 就**替代** `title`），**数据摊平归实现层**（`h5/menu.tsx` 用 `panels[i].trail[i-1].label` 算每层名字，根层用面板标题）。放共享头部的理由：面包屑是「通用头部」的能力，不是 menu 私有零件，否则 `menu-parts` 要反向引用 `--bv-panel-header-*` token。
- **槽名**：`panel-header-breadcrumb`（`nav[aria-label]`）/ `-crumb`（祖先，可点 `<button>`）/ `-crumb-current`（当前层，`<span aria-current="true">`）/ `-crumb-separator`。
- **三条取舍**：① **单层不铺** —— 只有一层时铺面包屑没有意义，由调用方按 `levels.length > 1` 决定，根层退化为普通居中标题 → 视觉零回归（共享零件**不做层数判断**，那是调用方的语义）；② **当前层不可点**并标 `aria-current`（已经在那一层，点了没有意义），祖先层才给 `onSelect`（`path` 截断到该层）；③ **横向可滚 + 自动滚到末端**，滚动 effect 的依赖用**层数**（`breadcrumb?.length`）而非数组本身 —— 数组每次渲染都是新身份，那样会在无关渲染里反复把视野拽回末端。
- **返回箭头保留**：与面包屑并存（左键「逐层退」、链上「跨层跳」），两种粒度各解决一种需求。
